# پیگیر ۴.۶ - سرور شخصی و شرکت‌های مستقل

این بسته روی Ubuntu با Docker اجرا می‌شود. یک API مشترک، برای هر شرکت یک فایل SQLite مستقل دارد؛ حساب مدیر سامانه و فهرست شرکت‌ها در پایگاه جدا هستند. کد شرکت در تمام درخواست‌های اندروید ارسال می‌شود. نام کاربری تکراری در شرکت‌های مختلف مجاز است. توکن شرکت اول در شرکت دوم معتبر نیست؛ دسترسی کاربران عادی فقط به مصوبات خودشان و جلسات دعوت‌شده محدود است.

مدیر سامانه از پنل وب شرکت و نخستین مدیر را می‌سازد. نام و نام کاربری متعلق به شخص هستند؛ «مدیر»، «دستیار» و «کاربر» نقش‌های قابل تعیین‌اند. هر شرکت می‌تواند چند مدیر داشته باشد. مدیر نقش‌ها را تعیین می‌کند و دستیار فقط کاربران عادی را مدیریت می‌کند. تأیید نهایی مصوبهٔ واگذارشده با مدیر است. پنل سامانه، شرکت‌ها را مدیریت می‌کند و محتوای جلسات آن‌ها را نمایش نمی‌دهد.

## ارتقای چندشرکتی گوشی - ۴.۶

هر نصب اندروید می‌تواند چند حساب شرکت را نگه دارد. پروتکل کاری ۲ تغییر نکرده است. migration افزایشی `0004_push_accounts.sql` ثبت دستگاه را با شناسهٔ حساب روی گوشی مستقل می‌کند؛ همان توکن FCM می‌تواند در چند شرکت و حتی چند حساب یک شرکت ثبت شود. نشست، نقش و مجوز مشاهده همچنان از توکن معتبر هر حساب تعیین می‌شوند؛ `accountRoute` مجوز دسترسی نیست. شناسه فقط برای مسیریابی اعلان روی گوشی استفاده می‌شود و به کاربر دیگری قابل تصاحب نیست.

برای نصب موجود، فقط کد جدید را جایگزین و سرویس api را بازسازی کنید. Registry هنگام بازشدن پایگاه هر شرکت، جدول جدید را به‌صورت idempotent ایجاد می‌کند؛ داده‌ها و دستگاه‌های قدیمی حفظ می‌شوند. پس از ارتقا health برابر 4.10.0 است. راهنمای Nginx مراحل دقیق را دارد. نیازی به ساخت دوبارهٔ شرکت‌ها، تغییر کلیدهای Firebase یا اجرای init نیست. چند سرور متفاوت برای داده پشتیبانی می‌شوند؛ اعلان فوری این نسخه روی گوشی از پروژهٔ Firebase مشترک پیگیر استفاده می‌کند. در صورت تفاوت پروژهٔ سرورها، برنامه خطای همان حساب را نشان می‌دهد و اطلاعات پروژهٔ قبلی را جایگزین نمی‌کند.

## سرور دارای Nginx

برای سرور دارای Nginx، از [راهنمای مخصوص peygir.hydrocode.ir](NGINX-fa.md) و `compose.nginx.yaml` استفاده کنید. این حالت فقط API را روی `127.0.0.1:18300` منتشر می‌کند؛ Nginx میزبان HTTPS را مدیریت می‌کند. میان‌بر `sudo bash vps/scripts/peygir-nginx.sh ...` تمام فرمان‌های Compose را به همین حالت هدایت می‌کند. بستهٔ جداگانهٔ `Peygir-4.10.0-nginx-vps.zip` شامل سورس کامل سرور و راهنمای `START-HERE-fa.md` است.

بخش «راه‌اندازی نخست» پایین مربوط به حالت مستقل Caddy است؛ روی سرور دارای Nginx، مراحل راهنمای اختصاصی را اجرا کنید. برای پشتیبان/بازیابی/import هم فایل Compose حالت انتخابی را حفظ کنید تا Caddy ناخواسته بالا نیاید.

## ارتقای نسخهٔ ۴.۳ و اعلان دعوت/واگذاری

API نسخهٔ ۴.۳ نوع رویداد اعلان را برای هر گیرنده تعیین می‌کند: دعوت جدید فقط برای فرد اضافه‌شده، واگذاری جدید فقط برای مسئول تازه، و تغییر عادی برای سایر ویرایش‌ها. مدیران ناظر که خودشان دعوت/مسئول نیستند، پیام به‌روزرسانی عمومی می‌گیرند. رویداد تراکنشی و حذف تکراری حفظ شده است؛ متن/نام/شرح جلسات و مصوبات همچنان به Firebase فرستاده نمی‌شود.

ابتدا کد سرور، سپس APK ۴.۳ را روی گوشی‌ها جایگزین کنید. schema و کلیدهای FCM و حساب‌ها تغییری ندارند. پوشهٔ `.device-private`، volumeها، گواهی Nginx و رمزهای قبلی را نگه دارید؛ init را تکرار نکنید. در سرور دارای Nginx، پس از جایگزینی فایل‌های بسته:

```bash
sudo bash vps/scripts/peygir-nginx.sh up -d --build --wait --wait-timeout 90 api
curl --fail http://127.0.0.1:18300/health
```

پاسخ سلامت بستهٔ فعلی نسخهٔ `4.10.0` است. توضیح زیر دربارهٔ تغییرات تاریخی ۴.۳ است. در حالت Caddy، همین به‌روزرسانی سرویس api با فایل Compose اصلی انجام می‌شود. اعلان در حالت باز و پس‌زمینه از FCM با اولویت بالا دریافت می‌شود؛ مجوز و کانال اعلان و تنظیم «یادآوری در این گوشی» باید فعال باشند. توقف اجباری یا محدودیت باتری/شبکه، دریافت فوری را تضمین‌پذیر نمی‌کند. پس از ارتقا، دعوت/واگذاری تازه‌ای برای آزمون ثبت کنید؛ رویدادهای قبلی دوباره ارسال نمی‌شوند.

## مخاطبان و ورود صوتی در نسخهٔ ۴.۲

مخاطب با حساب کاربری فرق دارد. نام تازهٔ مسئول بدون حساب یا مهمان جلسه، هنگام ثبت معتبر در جدول `contacts` پایگاه همان شرکت ذخیره می‌شود؛ هیچ نشست، نقش یا اعلان به آن تعلق نمی‌گیرد. مدیر و دستیار همان شرکت فهرست نام‌ها را در همگام‌سازی دریافت می‌کنند. کاربر عادی فقط اطلاعات مجاز مصوبات/دعوت‌های خودش را می‌گیرد و فهرست کامل مخاطبان را نمی‌گیرد. حذف رکورد کاری نام مخاطب را پاک نمی‌کند.

انتخاب کاربر فعال از پیشنهاد مسئول، شناسهٔ حساب او را در مصوبه ثبت می‌کند. تایپ یا تشخیص صوتی نام به‌تنهایی واگذاری نیست؛ کاربر نام پیشنهادی را تأیید می‌کند. مهمان جلسه در `guests` نام دارد و شرکت‌کنندهٔ دارای حساب در `attendees` شناسه دارد. کپی و تکرار جلسه هر دو فهرست را حفظ می‌کنند؛ اعلان فقط به حساب‌های مجاز می‌رسد. ویرایش جلسه با کلاینت قدیمی که فیلد مهمان را نمی‌شناسد، مهمان‌های موجود را پاک نمی‌کند.

ابتدا بستهٔ سرور ۴.۲ را جایگزین و طبق دستورهای Docker همین راهنما بازسازی کنید؛ سپس APK ۴.۲ (کد ۳۰) را روی نسخهٔ قبلی نصب کنید. در نخستین دسترسی، جدول مخاطبان برای شرکت‌های قبلی نیز به شکل تکرارپذیر ساخته می‌شود. فایل‌های SQLite و حجم داده را نگه دارید. پشتیبان سرور همان قالب ۱ است؛ پشتیبان گوشی ۵، قالب‌های ۱ تا ۴ را می‌خواند. بازگشت APK به نسخهٔ قدیمی پس از ارتقای پایگاه گوشی به ۷ پشتیبانی نمی‌شود.

صوت فیلدها فقط روی گوشی با Vosk تبدیل می‌شود؛ فایل موقت پس از تبدیل/انصراف حذف می‌شود و به VPS یا Firebase ارسال نمی‌شود. برای این بخش مدل یا تنظیم سروری جدید لازم نیست. دریافت واقعی میکروفون و کیفیت تشخیص نام‌ها باید روی گوشی نهایی بررسی شود.

## پیش‌نیاز

- Ubuntu 64-bit، Docker Engine و افزونهٔ Docker Compose v2: [راهنمای رسمی نصب](https://docs.docker.com/engine/install/ubuntu/).
- دامنه‌ای مانند `sync.example.com` با رکورد A/AAAA صحیح به VPS؛ پورت‌های ۸۰ و ۴۴۳ باز باشند. در حالت مستقل Caddy این پورت‌ها را دارد؛ در حالت Nginx موجود، API فقط روی loopback منتشر می‌شود. SQLite پورت عمومی ندارد.
- فضای دیسک برای داده و پشتیبان. نام دامنه را در فرمان‌های نمونه با دامنهٔ خودتان عوض کنید.

فرمان‌ها Bash و از ریشهٔ بسته هستند؛ جایی که پوشه‌های `vps` و `cloudflare` قرار دارند. نیاز به نصب Node یا npm روی Ubuntu نیست.

## راه‌اندازی نخست

```bash
docker run --rm --user "$(id -u):$(id -g)" \
  -v "$PWD:/workspace" -w /workspace \
  node:24.21.0-bookworm-slim \
  node vps/scripts/init.mjs --domain sync.example.com

docker compose --env-file .device-private/vps/compose.env \
  -f vps/compose.yaml up -d --build
```

اسکریپت، رمز تصادفی مدیر سامانه و فایل‌های تنظیمات را در `.device-private/vps` می‌سازد و رمز را در خروجی ترمینال چاپ نمی‌کند. اطلاعات ورود در `owner-login.txt` همان پوشه است؛ آن را فقط روی سیستم خودتان بخوانید. اجرای دوباره، تنظیمات موجود را بازنویسی نمی‌کند. این پوشه وارد Git، کانتینر یا بستهٔ سورس تحویلی نمی‌شود.

پوشهٔ خصوصی مجوز ۷۰۰ دارد. فایل‌های JSON داخل آن ۶۴۴ هستند تا Compose آن‌ها را به‌صورت secret برای کاربر غیرریشهٔ API قابل خواندن کند؛ پوشهٔ خصوصی را عمومی یا قابل دسترسی برای کاربران دیگر نکنید. [مستندات secrets در Compose](https://docs.docker.com/compose/how-tos/use-secrets/).

بستهٔ اولیهٔ init تحت umask ۰۷۷، مجوز درخواستی ۶۴۴ را به ۶۰۰ تبدیل می‌کرد و API غیرریشه خطای `EACCES` می‌گرفت. این ایراد در init اصلاح شده است: سه JSON mountشده پس از ساخت، chmod صریح ۶۴۴ می‌شوند؛ فایل ورود و تنظیمات ۶۰۰ و پوشه ۷۰۰ هستند. برای فایل‌های موجود، بدون اجرای دوبارهٔ init:

```bash
chmod 700 .device-private/vps
chmod 644 .device-private/vps/admin-bootstrap.json \
  .device-private/vps/fcm-service-account.json \
  .device-private/vps/fcm-public.json
chmod 600 .device-private/vps/owner-login.txt .device-private/vps/compose.env
```

سپس فقط API را با Compose حالت انتخاب‌شده recreate کنید. برای Nginx، [دستور رفع خطای نصب موجود](NGINX-fa.md#رفع-خطای-eacces-در-بستهٔ-اولیه) آماده است. محتوا و رمزها تغییر نمی‌کنند.

پس از آماده‌شدن دامنه، نشانی `https://sync.example.com/admin/` را باز کنید. Caddy گواهی HTTPS را صادر و تمدید می‌کند؛ دادهٔ گواهی در volume جدا باقی می‌ماند. [شرایط HTTPS خودکار](https://caddyserver.com/docs/automatic-https#overview).

## راه‌اندازی هر شرکت

۱. با حساب مدیر سامانه وارد پنل شوید و «شرکت جدید» را بزنید.

۲. نام شرکت، کد انگلیسی یکتا و نام رئیس را وارد کنید. کد بین ۳ تا ۳۲ نویسه، شامل حروف کوچک انگلیسی، عدد و خط تیره است و پس از ثبت تغییر نمی‌کند. نام کاربری پیش‌فرض رئیس `manager` است؛ زیر «جزئیات بیشتر» قابل تعیین است. رمز قوی خودکار ساخته می‌شود یا می‌توانید رمز حداقل ۱۲ نویسه‌ای تعیین کنید.

۳. پنجرهٔ نتیجه، نشانی سرویس، کد شرکت، نام کاربری و رمز را فقط همان بار نشان می‌دهد؛ دکمهٔ کپی یا ذخیرهٔ فایل دارد. اطلاعات را خودتان به مدیر همان شرکت بدهید.

۴. APK نسخهٔ ۴ را روی گوشی نصب کنید. پس از مجوزها، چهار فیلد ورود را پر کنید: نشانی HTTPS سرویس، کد شرکت، نام کاربری و رمز.

۵. مدیر از تنظیمات ← حساب و همگام‌سازی ← حساب‌های شرکت ← کاربر جدید، نام و نام کاربری فرد را ثبت و نقش مدیر، دستیار یا کاربر را انتخاب می‌کند. هر حساب فقط در همان شرکت معتبر است. تعلیق شرکت، ورود و همگام‌سازی آن شرکت را قطع و نشست‌ها را باطل می‌کند؛ اطلاعات حفظ می‌شوند. فعال‌سازی دوباره به ورود تازه نیاز دارد.

## ویرایش و حذف کاربران

از منوی سه‌نقطهٔ هر حساب، «ویرایش حساب»، بازیابی رمز، فعال/غیرفعال‌کردن و «حذف کاربر» در دسترس است. مدیر نام، نام کاربری و نقش را ویرایش می‌کند؛ دستیار فقط کاربران عادی را مدیریت می‌کند و نمی‌تواند نقش مدیر یا دستیار بدهد.

تغییر نام، شناسهٔ شخص و ارتباط مصوباتش را حفظ می‌کند. تغییر نام کاربری یا نقش، نشست‌های قبلی آن کاربر را باطل می‌کند و ورود دوباره لازم است. پیش از تغییر حساب خودتان، تغییرهای ارسال‌نشدهٔ گوشی را همگام کنید. حذف خودتان و حذف یا تنزل آخرین مدیر فعال مجاز نیست؛ بررسی آخرین مدیر داخل تراکنش انجام می‌شود.

حذف کاربر با تأیید انجام می‌شود: ردیف حساب، نشست‌ها، ثبت دستگاه و صف اعلان او حذف می‌شوند؛ مصوبات و سوابق کاری حفظ می‌شوند و مدیر می‌تواند مسئولشان را عوض کند. نام کاربری آزادشده را می‌توان برای حسابی تازه با شناسه و دسترسی تازه استفاده کرد؛ حساب تازه مصوبات حساب حذف‌شده را به ارث نمی‌برد. شناسهٔ حذف‌شده برای ساخت حساب جدید قابل استفاده نیست.

قطع دسترسی سرور فوری است؛ پاک‌شدن نسخهٔ دریافت‌شده از گوشیِ آفلاین تا اتصال و بررسی نشست آن گوشی به تأخیر می‌افتد. بازیابی رمز مدیر شرکت از پنل سامانه، اگر مدیر اولیه حذف یا تغییر نقش داده باشد، یک مدیر فعال دیگر را انتخاب می‌کند.

این قابلیت‌ها به سرور و APK نسخهٔ ۴.۱ نیاز دارند؛ هر دو بسته را با هم ارتقا دهید. پایگاه‌ها و پشتیبان‌های نسخهٔ ۴.۰ سازگارند و نصب دوباره یا حذف داده لازم نیست.

## اعلان فوری با Firebase

حساب‌ها، مجوزها و اطلاعات مشترک روی VPS هستند. Firebase فقط برای رساندن اعلان عمومیِ تغییر به گوشی استفاده می‌شود؛ پیام آن شامل شناسه‌ها، نوع رویداد و کد شرکت است و عنوان یا شرح جلسه/مصوبه را ندارد. دریافت اطلاعات اصلی از API شخصی است. یادآوری موعدهای دریافت‌شده و مرور صبح روی گوشی اجرا می‌شوند.

فایل‌های `{}` اولیه اجازه می‌دهند سرویس بدون FCM هم راه بیفتد؛ همگام‌سازی هنگام بازبودن اپ و بررسی دوره‌ای برقرار است، ولی اعلان فوری تا تنظیم FCM فعال نمی‌شود.

- JSON حساب سرویس Firebase را در `.device-private/vps/fcm-service-account.json` بگذارید.
- تنظیم عمومی اپ را در `.device-private/vps/fcm-public.json` قرار دهید:

```json
{
  "projectId": "your-firebase-project",
  "applicationId": "1:123456789:android:YOUR_FIREBASE_APP_ID",
  "senderId": "123456789",
  "apiKey": "YOUR_FIREBASE_ANDROID_API_KEY"
}
```

`applicationId` شناسهٔ اپ در Firebase است؛ شناسهٔ بستهٔ اندرویدی `ir.peygir.app` نیست. شناسهٔ پروژهٔ دو فایل باید یکی باشد. فایل عمومی از `google-services.json` پروژهٔ خودتان قابل استخراج است؛ کلید خصوصی حساب سرویس فقط در سرور می‌ماند.

```bash
chmod 700 .device-private/vps
chmod 644 .device-private/vps/*.json
docker compose --env-file .device-private/vps/compose.env \
  -f vps/compose.yaml up -d --force-recreate api
```

سپس در اپ همگام‌سازی کنید و بخش «اعلان فوری» را بررسی کنید. صف اعلان در پایگاه همان شرکت نگهداری می‌شود و سرویس هر دقیقه ارسال‌های ناموفق را بازبینی می‌کند. اجازهٔ اعلان، اتصال گوشی و محدودیت‌های اندروید همچنان مؤثرند.

## پشتیبان‌گیری سرور

پشتیبان درون اپ مربوط به همان گوشی است. ابزار زیر همهٔ شرکت‌های سرور و فهرست مدیریتی را با SQLite Backup API پشتیبان می‌گیرد؛ از کپی ناقص فایل‌های WAL استفاده نمی‌کند. API برای مدت کوتاه متوقف می‌شود تا تصویر تمام شرکت‌ها هماهنگ باشد؛ قفل SQLite مانع اجرای اشتباهی ابزار روی API فعال است.

```bash
docker compose --env-file .device-private/vps/compose.env -f vps/compose.yaml stop api
docker compose --env-file .device-private/vps/compose.env -f vps/compose.yaml \
  run --rm --no-deps api node vps/scripts/backup.mjs
docker compose --env-file .device-private/vps/compose.env -f vps/compose.yaml start api
```

نام پوشهٔ ساخته‌شده زیر `/backups` چاپ می‌شود. آن را با فرمان زیر خارج از VPS هم نگهداری کنید؛ `BACKUP_NAME` را با همان نام عوض کنید:

```bash
umask 077
docker compose --env-file .device-private/vps/compose.env -f vps/compose.yaml \
  run --rm --no-deps api tar -C /backups -czf - BACKUP_NAME > peygir-server-backup.tgz
```

پوشهٔ خصوصی تنظیمات و کلیدهای FCM را نیز جداگانه و امن نگهداری کنید؛ در پشتیبان پایگاه‌ها قرار نمی‌گیرند. volume پشتیبان روی همان VPS به‌تنهایی جای نسخهٔ خارج از سرور را نمی‌گیرد.

## بازیابی روی volume تازه

بازیابی روی اطلاعات موجود بازنویسی نمی‌کند. ابتدا سرویس را پایین بیاورید؛ از `down -v` استفاده نکنید:

```bash
docker compose --env-file .device-private/vps/compose.env -f vps/compose.yaml down
```

در فایل خصوصی `compose.env` فقط `PEYGIR_DATA_VOLUME` را به نام تازه‌ای مثل `peygir_data_restored_01` تغییر دهید. نام volume پشتیبان را حفظ کنید. سپس:

```bash
docker compose --env-file .device-private/vps/compose.env -f vps/compose.yaml \
  run --rm --no-deps api node vps/scripts/restore.mjs --from /backups/BACKUP_NAME --confirm
docker compose --env-file .device-private/vps/compose.env -f vps/compose.yaml up -d
```

ابزار ابتدا اثر انگشت، ساختار SQLite، کلیدهای خارجی و کامل‌بودن مجموعهٔ شرکت‌ها را بررسی می‌کند. پس از بازیابی، مدیر سامانه و کاربران شرکت‌ها باید دوباره وارد شوند؛ نشست‌های قبلی و ثبت دستگاه‌ها باطل می‌شوند تا گوشی‌ها اطلاعات بازیابی‌شده را از نو دریافت کنند و اعلان‌های قدیمی تکرار نشوند. اگر خطای دیسک بازیابی را نیمه‌کاره کرد، از volume تازهٔ دیگری استفاده کنید؛ volume قبلی تا تصمیم شما باقی می‌ماند.

## انتقال شرکت فعلی از Cloudflare

این مرحله بعد از استقرار VPS انجام می‌شود؛ این بسته خودش به Cloudflare واقعی وصل یا چیزی را حذف نمی‌کند.

۱. همهٔ گوشی‌ها را با سرویس قبلی همگام کنید تا تغییر ارسال‌نشده نماند و از اطلاعات گوشی‌ها پشتیبان بگیرید. هنگام انتقال، ثبت/ویرایش روی سرویس قدیمی را متوقف کنید.

۲. با دسترسی مالک Cloudflare، خروجی کامل SQL بگیرید و فایل را خصوصی نگه دارید:

```bash
# این فرمان در سورس پروژهٔ فعلی و با حساب Cloudflare مالک اجرا می‌شود.
cd cloudflare
npx wrangler d1 export DB --remote --output ../.device-private/company-export.sql
```

۳. فایل SQL را خودتان به VPS منتقل کنید. پیش از انتقال از سرور VPS هم پشتیبان بگیرید، سپس API را متوقف کنید. فایل را با کانتینر یک‌باره در volume پشتیبان کپی کنید:

```bash
docker compose --env-file .device-private/vps/compose.env -f vps/compose.yaml stop api
docker compose --env-file .device-private/vps/compose.env -f vps/compose.yaml \
  run --rm --no-deps -v "$PWD/.device-private/company-export.sql:/import/company.sql:ro" \
  api node vps/scripts/import-d1.mjs --sql /import/company.sql --code company-code --name "نام شرکت"
docker compose --env-file .device-private/vps/compose.env -f vps/compose.yaml start api
```

شرکت را قبل از import در پنل نسازید؛ ابزار خودش آن را اضافه می‌کند. ورود قبلی مدیر سامانه باید یک‌بار انجام شده باشد تا پایگاه مدیریتی آماده باشد. import فقط خروجی تک‌شرکتی با ساختار سازمانی فعلی را می‌پذیرد، شناسه‌ها، رمزها، جلسات و مصوبات را حفظ می‌کند و نشست‌ها/ثبت دستگاه‌های قدیمی را پاک می‌کند. شرکت موجود بازنویسی نمی‌شود. فایل SQL صرفاً از مسیر آفلاین مدیر سرور پذیرفته می‌شود و API بارگذاری SQL ندارد.

۴. APK نسخهٔ ۴ را روی نسخهٔ قبلی نصب کنید. پس از اطمینان از انتقال کامل، در گوشی از حساب قبلی خارج شوید و با نشانی جدید، کد شرکت و همان نام کاربری/رمز وارد شوید. خروج از حساب، نسخهٔ محلی شرکت را پاک و ورود تازه آن را از VPS دریافت می‌کند؛ تغییرهای ارسال‌نشده را قبل از خروج حتماً ارسال کنید. برنامه را حذف نکنید.

تا پایان بررسی روی چند گوشی، سرویس قدیمی را نگه دارید؛ ثبت هم‌زمان روی دو سرور انجام ندهید. [راهنمای رسمی خروجی D1](https://developers.cloudflare.com/d1/best-practices/import-export-data/).

## نگهداری و بازیابی حساب مالک

```bash
# وضعیت
docker compose --env-file .device-private/vps/compose.env -f vps/compose.yaml ps
# لاگ بدون چاپ رمزها
docker compose --env-file .device-private/vps/compose.env -f vps/compose.yaml logs --tail 100 api

docker compose --env-file .device-private/vps/compose.env -f vps/compose.yaml up -d --build
```

برای رمز تازهٔ مدیر سامانه، API را متوقف و ابزار زیر را اجرا کنید؛ رمز در فایل خصوصی volume پشتیبان نوشته می‌شود و در لاگ چاپ نمی‌شود:

```bash
docker compose --env-file .device-private/vps/compose.env -f vps/compose.yaml stop api
docker compose --env-file .device-private/vps/compose.env -f vps/compose.yaml \
  run --rm --no-deps api node vps/scripts/reset-owner.mjs
docker compose --env-file .device-private/vps/compose.env -f vps/compose.yaml start api
```

برای توسعهٔ محلی Node 24.21+ تا قبل از 25 و اجرای `npm ci --prefix vps` لازم است؛ وابستگی اعلان وب با lockfile نصب می‌شود. `node --test vps/test/*.test.mjs` آزمون‌های جداسازی، دسترسی، نشست مدیریت، تداخل عملیات، import و پشتیبان را اجرا می‌کند. استقرار دامنهٔ عمومی و تحویل FCM روی گوشی واقعی باید هنگام راه‌اندازی VPS شما بررسی شوند.
