# انتشار خودکار وب و API روی نصب فعلی

Workflow موجود در `.github/workflows/android-update.yml` با نام **Peygir release** وب/API را هم منتشر می‌کند. همان Secrets و Variables انتشار اندروید استفاده می‌شوند؛ Secret جدید لازم نیست. این مسیر مخصوص نصب Docker با Nginx و پوشهٔ خصوصی فعلی است؛ نصب اولیه و انتشار Cloudflare را انجام نمی‌دهد.

## اولین اجرا

۱. تغییرات را commit و روی `main` push کنید. در GitHub به Actions → **Peygir release** بروید.

۲. Run workflow، شاخهٔ `main` و گزینهٔ `check` را انتخاب کنید. باید هر دو پیام `VPS_CONNECTION_OK` و `SERVER_CONNECTION_OK` دیده شوند. این حالت سرویس را متوقف یا منتشر نمی‌کند.

۳. برای ارتقای فقط وب/API، دوباره Run workflow را با شاخهٔ `main` و گزینهٔ `deploy-server` اجرا کنید. نسخهٔ ۴.۱۱.۰ از `vps/package.json` خوانده می‌شود. دیگر لازم نیست ZIP را دستی انتقال دهید. موفقیت با job **Back up and upgrade web/API on VPS** و پیام `SERVER_DEPLOYED` مشخص می‌شود.

اگر در همین انتشار، APK جدید هم لازم است، پس از بررسی اتصال تگ `v4.11.1` را روی commit جدید `main` push کنید؛ اجرای جداگانهٔ `deploy-server` الزامی نیست. نسخهٔ اندروید ۴.۱۱.۱ با API نسخهٔ ۴.۱۱.۰ منتشر می‌شود. تگ استفاده‌شده را جابه‌جا یا بازنویسی نکنید. اجرای مجدد تگ ناموفق قبلی، اصلاحات commit جدید را دریافت نمی‌کند.

```bash
git tag -a v4.11.1 -m "Peygir 4.11.1"
git push origin v4.11.1
```

برای انتشارهای بعدی، شمارهٔ نسخه و یادداشت انتشار اندروید را مطابق [راهنمای انتشار اپ](AUTOMATIC-UPDATES-fa.md) تغییر دهید؛ نسخهٔ سرور را هنگام تغییر وب/API در `vps/package.json` و lockfile و پاسخ `/health` هم به‌روز کنید.

## ترتیب انتشار

- آزمون‌های سرور، مرورگر و ابزارهای انتشار اجرا می‌شوند. هنگام انتشار تگ، ساخت و امضای اندروید نیز باید موفق باشد.
- فقط سورس عمومی لازم برای سرور به پوشه‌ای خصوصی زیر نصب قبلی منتقل می‌شود؛ هش آرشیو و تک‌تک فایل‌ها بررسی می‌شود.
- image جدید روی VPS ساخته می‌شود؛ API قبلی در طول ساخت فعال است. نام پروژه و نام دقیق volumeهای داده و پشتیبان با کانتینر فعلی مقایسه می‌شوند؛ اختلاف، انتشار را پیش از توقف مسدود می‌کند.
- API برای پشتیبان‌گیری سازگار SQLite متوقف می‌شود. نسخهٔ قبلی ابزار backup، registry و تمام شرکت‌ها را در volume فعلی `/backups` پشتیبان می‌گیرد. سپس نسخهٔ جدید، مهاجرت‌های افزایشی و سلامت پایگاه تمام شرکت‌ها، حتی شرکت‌های غیرفعال را بررسی می‌کند.
- کانتینر API با image جدید راه می‌افتد. سلامت Docker، نسخهٔ API داخل کانتینر و `/health` روی دامنهٔ HTTPS بررسی می‌شوند. Nginx میزبان تغییر نمی‌کند.
- پس از موفقیت سرور، APK منتشر می‌شود. اگر هش سورس و نسخهٔ سرور با image فعال یکی باشد، ارتقای سرور بدون ری‌استارت رد می‌شود.

در بخش پشتیبان‌گیری، مهاجرت و راه‌اندازی، وقفهٔ کوتاه سرویس وجود دارد؛ مدت آن به حجم داده‌ها بستگی دارد. فضای کافی برای image جدید و پشتیبان لازم است. Docker Compose باید از `!reset null` پشتیبانی کند؛ نبود این قابلیت پیش از توقف مشخص می‌شود.

## حفظ تنظیمات و بازگشت

پوشهٔ `.device-private`، تنظیمات Firebase، فایل `compose.env`، شرکت‌ها، حساب‌ها، APKهای موجود و volumeها حفظ می‌شوند. اسکریپت هیچ volume را حذف یا دوباره مقداردهی نمی‌کند. image قبلی با تگ `before-...` نگهداری می‌شود. در خطای پس از توقف، اسکریپت تلاش می‌کند image قبلی را دوباره اجرا کند و اجرای GitHub ناموفق می‌ماند.

این بازگشت، image برنامه را عوض می‌کند؛ پایگاه داده را خودکار به گذشته برنمی‌گرداند. مهاجرت‌های فعلی افزایشی و با API قبلی سازگارند. مهاجرت مخرب آینده به فرایند جداگانه و بررسی سازگاری نیاز دارد. در قطع برق یا خاتمهٔ اجباری فرایند، اجرای trap بازگشت تضمین نمی‌شود؛ سلامت سرویس را بررسی کنید.

پس از اولین انتشار، فایل خصوصی `.device-private/vps/deployed-api.yaml` image فعال و نام پروژه را تعیین می‌کند. ابزار `vps/scripts/peygir-nginx.sh` این فایل را خودکار می‌خواند؛ فرمان‌های وضعیت، log و پشتیبان‌گیری قبلی همچنان قابل استفاده‌اند:

```bash
cd /root/peygir/Peygir-VPS
sudo bash vps/scripts/peygir-nginx.sh ps
sudo bash vps/scripts/peygir-nginx.sh logs --tail 100 api
curl --fail https://peygir.hydrocode.ir/health
```

سورس قدیمی در پوشهٔ اصلی نصب بازنویسی نمی‌شود؛ کد اجرایی جدید داخل image است. پس از فعال‌شدن این روش، برای انتشار بعدی از همین Workflow استفاده کنید: `up --build` در حضور override همچنان image مدیریت‌شده را اجرا می‌کند. فایل‌های Compose نصب قبلی و کل پوشهٔ خصوصی را نگه دارید.

آرشیو سورس، مشخصات image، مسیر backup و نتیجهٔ موفق در `.device-private/vps/server-release.*/result.json` نگهداری می‌شوند. این فایل فقط پس از موفقیت کامل ساخته می‌شود. پاک‌سازی خودکار imageهای قبلی و پوشه‌های انتشار انجام نمی‌شود. artifact بستهٔ سرور در GitHub برای ۱۴ روز موجود است؛ پشتیبان دیتابیس روی VPS می‌ماند.

## خطا و تکرار

خطا در تست، ساخت image یا مقایسهٔ volumeها سرویس فعال را متوقف نمی‌کند. شکست backup یا مهاجرت مانع شروع نسخهٔ جدید می‌شود و بازگشت به image قبلی تلاش می‌شود. اگر خطای سلامت عمومی رخ داد، DNS، Nginx و خروجی job را بررسی کنید. ابتدا از فعال‌بودن سرویس قبلی مطمئن شوید، سپس Re-run failed jobs همان اجرا را بزنید. هنگام شکست سرور، APK جدید منتشر نمی‌شود.

این فرایند در محیط محلی با Docker و دادهٔ آزمایشی بررسی شده است؛ اولین اتصال و انتشار واقعی VPS باید از GitHub انجام شود.
